# Matriz de cumplimiento del PIA de FerreMax

Fecha de corte: 6 de noviembre de 2026. Equipo 17: Roberto Santana Trujillo e Isaías Leonardo Salazar Torres.

## Propósito y alcance de esta revisión

Relacionar cada requisito del profesor con documentos, componentes, pruebas y evidencia para organizar el cierre. Esta matriz es una herramienta de trabajo: no sustituye el BRD, el reporte final ni una aprobación del profesor.

Se inspeccionó el código de `52863c9f938f6aa89e34c59b62c7e13ce78f0d4d` (base de `pia-entrega`) y el PDF oficial **PIA_CLN_Proyecto_Integrador_AD2026.pdf**, sus cuatro páginas. Las fuentes históricas U2/U3 se mantienen intactas. El formato del futuro reporte será **U4_Informe.docx**; no se elaboró ese reporte en este bloque.

La comprobación técnica reutiliza evidencia identificada por commit. No se ejecutaron nuevas escrituras sobre la API pública ni sobre la base de demostración para elaborar la matriz. Las métricas CI/CD que se citan son las registradas, no una ejecución nueva atribuida a este documento.


## Actualización del bloque de análisis

Se integraron BRD, veinte historias, cuarenta y seis criterios Gherkin, BPMN descriptivo editable en siete vistas y glosario. R02-R05 acreditan ahora la existencia e integración de esos artefactos de análisis; R12 acredita la estructura documental mínima. R16 sigue parcial porque varios procesos del negocio aún carecen de implementación y pruebas integrales. No se considera resuelto por documentar su ausencia.

## Actualización de documentos de entrega

Se generaron informe PDF/Word y presentación PPTX/PDF en reporte/, con formato de referencia U4. Se verificaron nombres, matrículas, contenido de las veinte historias, fuente de evidencias, estructura de los editables y páginas PDF. R32 y R34 acreditan los archivos disponibles, no su entrega en NetAcad ni la defensa.

## Actualización de arquitectura y cierre

Se completan modelo DDD, cinco vistas de arquitectura, siete ADR, justificación de patrones/SOLID, índices y trazabilidad arquitectural. El contrato OpenAPI se regenera desde la aplicación actual. R06-R11, R14 y R18 pasan a Cumple documental para el núcleo descrito. R16 continúa Parcial: registrar límites no implementa procesos ausentes ni constituye una dispensa del profesor. Los resultados recientes registrados son 249 pruebas aprobadas, cero omitidas y 97.38% en c4876ef (CI 42322301835). El estado efectivo de integración y despliegue se consulta en [CIERRE.md](CIERRE.md).

## Estados

| Estado | Significado |
| --- | --- |
| Cumple | Existe el elemento y hay evidencia para el alcance indicado. Debe mantenerse en la versión final. |
| Parcial | Existen bases o componentes, pero falta integración, actualización o correspondencia completa. |
| Pendiente | No existe el entregable final solicitado. |
| Por realizar | La actividad ante el profesor aún debe ocurrir; una prueba automática no la sustituye. |

## Cobertura de las 20 historias de U2

**Decisión de alcance aún necesaria:** el PDF exige una solución coherente con el análisis. U3 delimitó un núcleo de contado y una ubicación por pedido, pero eso no equivale a que el profesor haya eximido las demás historias. Conservar las 20 historias no basta para declarar su cumplimiento. Antes de cerrar R02/R03/R16 se debe acordar qué procesos forman parte del alcance ejecutable del PIA y resolver los huecos obligatorios; cualquier limitación restante debe quedar explícita en el análisis y la defensa.
